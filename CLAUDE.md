## Conventions

- TypeScript 6.0, `strict` + `noUncheckedIndexedAccess` (from `packages/config/tsconfig/base.json`). Configuration is kept TypeScript-7-clean (no `baseUrl`, no `node10` resolution); see ADR 0007.
- Versions are pinned exactly in the `catalog:` of `pnpm-workspace.yaml`; workspaces reference them as `"catalog:"`. When adding a dependency, put its version in the catalog.
- ESM everywhere. In `apps/api` and `packages/shared` (`module: nodenext`) relative imports carry the `.js` extension: `import { x } from './x.js'`.
- `packages/shared` is consumed from its `dist/`; turbo builds it before dependants (`dependsOn: ["^build"]`). Run `pnpm --filter @beso/shared build` after changing it if you are not using `pnpm dev`.
- Lint: oxlint with `--type-aware`, per-workspace `.oxlintrc.json` extending `packages/config/oxlint/base.json`. Format: Prettier only (no ESLint).
- Tests: Vitest in every workspace. Naming: `*.spec.ts` unit tests next to the source in `apps/api`; `*.test.ts(x)` in `apps/web` and `packages/shared`; `test/*.int-spec.ts` integration tests in `apps/api`.
- Validation schemas and DTO types that both the API and the web need go in `packages/shared` (zod 4), never duplicated. In the API a DTO is `class XDto extends createZodDto(xSchema) {}` (nestjs-zod); the global `ZodValidationPipe` validates bodies/queries/params typed with such DTOs.
- API conventions (`apps/api/src/app.setup.ts`, `common/filters/api-exception.filter.ts`): routes live under `/api/v1`; `GET /health` is outside the prefix; every error is the shared `ApiError` envelope `{ statusCode, code, message, fields?, requestId }` (throw Nest `HttpException`s, optionally with `{ code, message, fields }`; Prisma P2002/P2025 are mapped automatically; unexpected errors become a masked 500 and are logged); every response has `X-Request-Id`; Swagger UI at `/api/docs` and JSON (OpenAPI 3.1) at `/api/docs/openapi.json` outside production. Every JSON handler declares its answer with `@ZodResponse({ status, type: XDto })` (replacing `@HttpCode`; the DTOs live in `common/responses.dto.ts`, one per shared schema, since several modules answer the same shape): the global `ZodSerializerInterceptor` parses the answer with the shared schema (unknown keys are dropped, so a stray selected column never leaves; a mismatch is a masked 500 logged with the failing paths, never a 400) and OpenAPI documents it. `204` handlers keep `@HttpCode(204)`; only `GET /health` (terminus documents it) and the upload file stream have no response schema.
- Logging: inject `Logger` from `@nestjs/common` (backed by pino via nestjs-pino); pino-style calls `logger.log({ userId }, 'message')`. Never `console.log` in `src/`. The client address is `req.ip` everywhere (request log `req.ip`, sessions, throttles, captcha): Express resolves it through `trust proxy` (`TRUST_PROXY=1` behind Caddy, which sets `X-Forwarded-For` from Cloudflare's `CF-Connecting-IP`), never the socket peer; throttle keys group IPv6 by /64 (`normalizeIp`). `test/client-address.int-spec.ts` covers the chain.
- Rate limiting: `ThrottlerGuard` is global (`THROTTLE_*` env); tighten per route with `@Throttle({ default: { limit, ttl } })`, opt out with `@SkipThrottle()`.
- Auth: the `AuthGuard` is global, so every route needs a session unless the handler or controller has `@Public()`. Access tokens are signed and checked only by `AccessTokensService` in `tokens/` (`TokensModule` owns the JWT secret; the global guard and the chat gateway import it, never `AuthModule`). Read the caller with `@CurrentUser() user: AuthUser` (`{ id }`). Tokens live in httpOnly cookies (`access_token` 15 min JWT, `refresh_token` single-use, scoped to `/api/v1/auth`, `SameSite=Lax`); a `Bearer` header works too. CSRF: `common/origin-check.ts` refuses every POST/PUT/PATCH/DELETE (and the socket handshake) whose `Origin` is neither in `WEB_ORIGINS` nor the API's own host, with a 403 envelope; requests without an Origin (curl, supertest) pass. A browser on an unlisted origin therefore gets 403s, not CORS errors: add it to `WEB_ORIGINS`. Never trust ids from the request body for authorisation.
- Errors: use the helpers in `common/errors.ts` (`notFound`, `badRequest(message, fields?)`, `conflict`, `forbidden`, `unauthorized`, `validationError(fields)`); the filter derives `code` from the status. `UsersService.assertAvailable` is the shared uniqueness check; `UsersService.assertExists` / `PostsService.assertExists` for 404s on referenced ids.
- Route params go through the zod DTOs in `common/params.dto.ts` (`@Param() params: IdParamDto`), never `ParseUUIDPipe`, so malformed ids are `VALIDATION_ERROR`s keyed by the parameter. Every client-supplied id (params, bodies, socket payloads) uses the shared `uuidSchema`, which lower-cases it: Postgres stores uuids lower-case, and text keys built from ids (`direct_key`) and in-memory comparisons must agree with that.
- Every "me" response is `{ user: UserPrivate }` (`meResponseSchema`); every list is `{ items, nextCursor }` even when it is not paginated yet.
- Email (ADR 0010): mail goes through `email/EmailService` only (`MAILER` = `SmtpMailer` with `SMTP_URL` in production, `OutboxMailer` writing JSON files to `EMAIL_OUTBOX_DIR` elsewhere; integration tests read them with `test/setup/outbox.ts`). Every mail shows the logo from the web app (ADR 0010 amendment 2026-10-28): `mailLogo(webUrl)` in `email/brand.ts` is `${WEB_URL}/mail-logo.png` with its CSS size (`mail-logo.ts`, generated) and every template takes it; the picture is the wordmark on a white tile, so a client's dark mode cannot hide it, and mails carry no attachments (an inline `cid:` picture is dropped by some webmail and by Resend's preview). Links carry `email_tokens` (`EmailTokensService.issue/consume/voidAll`: hashed, single-use, kind-bound; `issue` returns null past the per-account limits in `EMAIL_TOKEN_POLICY`, ADR 0011). The access token carries `ev`; the `AuthGuard` answers 403 to unverified sessions unless the route has `@AllowUnverified()`, and the socket handshake refuses them. On the web `RequireAuth` holds an unverified session on `/verify-email`. `reset-password` responses are sessions (`startSession`); `verify-email` answers `{ user }` (a new access cookie) only to a browser whose refresh cookie belongs to that account and `{ user: null }` ("confirmed, now sign in") to any other: a mailed link must never sign a browser in by itself. Email change (ADR 0010 amendment): `POST /auth/email { newEmail, password }` stores `users.pending_email` and mails a `change_email` link to the **new** address (`sendEmailChangeConfirm`, notice to the old one); `POST /auth/email/confirm` swaps the address (re-checks uniqueness, a 409 drops the pending change), marks it verified, mails `sendEmailChanged` and signs nobody in (`{ email }`); `POST /auth/email/resend` / `DELETE /auth/email` manage the pending state; `pendingEmail` rides on every "me". Web: `features/settings/email-change-form.tsx` (used by the Settings → Email card and the waiting room), the link lands on `/confirm-email`. Sessions: `GET /auth/sessions` lists the live refresh tokens (`describeUserAgent` / `maskIp` in `auth/user-agent.ts`; `current` from the caller's cookie; `createdAt` carried along rotation, `lastUsedAt` stamped by it), `DELETE /auth/sessions/:id` ends one (`RefreshTokensService.revokeOne`, no socket disconnect); Settings → Sessions is `sessions-list.tsx` (tests seed `mockDb.sessions`). Password changes and resets mail a notice (`sendPasswordChanged`).
- Account lifecycle (ADR 0012): `account/` owns `DELETE /users/me` and `GET /users/me/export`. Deletion erases (one transaction: the user row and its cascades, plus the direct threads and last-member groups; `comments.reactions_count` of others' comments is decremented and `last_message_at` of groups that stay is recomputed first), then `sessions.revoked` cuts the sockets, `conversation.left` / `conversation.deleted` tell the others, `UploadsService.deleteFiles` removes the files, cookies are cleared and `sendAccountDeleted` mails a notice. Any new denormalised counter or per-user file must be handled there too. Both routes allow unverified sessions. The web side is the **Your account** card in Settings (`features/settings/account-card.tsx`; downloads go through `lib/download.ts`).
- Password change: `POST /auth/password` verifies the current password, re-hashes and calls `RefreshTokensService.revokeOthers(userId, currentRaw)` (other devices lose their refresh token, their access token runs out within 15 min; no socket disconnect is forced). Refresh-token `revokedAt` means "rotated" only (reuse detection); every other way a session ends deletes the rows, so a token of an ended session is merely invalid and can never trigger `revokeAll` against the sessions that remain. `logout-all` is the "sign out everywhere" path and does revoke + disconnect. The web `/settings` page (`features/settings/`) is the home for account-level options; add new ones there rather than to the account menu.
- Bot check (ADR 0012): registration goes through the `CAPTCHA` verifier (`captcha/`): `TurnstileVerifier` when `TURNSTILE_SECRET` is set, `NoopVerifier` otherwise; a refused token is a field error on `captchaToken`, an unreachable check is 503 `CAPTCHA_UNAVAILABLE` (never a pass). Production needs the secret or `CAPTCHA=off`. Integration tests swap it with `createTestApp({ overrides: (b) => b.overrideProvider(CAPTCHA).useValue(fake) })`. On the web the widget (`features/auth/turnstile.tsx`) renders only when `VITE_TURNSTILE_SITE_KEY` is built in (`getTurnstileSiteKey()`, read lazily so tests can `vi.stubEnv` it); tests stub `window.turnstile`.
- Credential routes (login/register) are marked `@CredentialRoute()`; that is what applies the per-account and per-address throttlers from `auth/credential-throttle.ts`.
- Realtime: `ChatGateway` (socket.io, same port) authenticates at handshake only; the global `AuthGuard` and `HttpThrottlerGuard` skip non-HTTP contexts (and `ApiExceptionFilter` only turns a handler's exception into an `exception` event), so never rely on them inside `@SubscribeMessage` handlers: validate payloads with the shared zod schemas and answer with an ack `{ ok, message | error }`. Deliver server pushes from domain events (`@OnEvent` in the gateway, rooms `user:<id>`; events carry the member ids and the gateway emits to each room through `emitTo`, which refuses an empty list because socket.io would broadcast to everyone), so HTTP and socket paths behave the same. Ephemeral signals that nothing stores (typing: `typing` in → `typing:update` out to the other members) are the one exception: relayed straight from the handler, no ack, rate-limited, invalid payloads and foreign conversations dropped silently, relays chained per socket so order holds; the client expires them on its own. Presence is in-memory (single instance) and broadcast at most once per `PRESENCE_BROADCAST_DELAY_MS`; handshakes are limited per user (`SOCKET_CONNECTS_PER_MINUTE`, default 30) as is the number of open sockets (`SOCKET_MAX_PER_USER`, default 5), both refused as `Too many connections`; the Playwright API raises them because every worker is signed in as alice, and a browser whose handshake was refused still sends over HTTP but receives no pushes until its next attempt (10 s later). Nest drops the promise of `handleConnection`, so nothing may escape it (a rejection would end the process): on failure it closes the transport (`socket.conn.close()`, the client retries with back-off), whereas `socket.disconnect(true)` means "session over, refresh".
- Scheduled jobs (ADR 0012 amendment): `jobs/JobsService.runDaily(now)` and `runFrequent(now)` (every five minutes, ADR 0012 "Frequent jobs": work due at a moment, idempotent by claiming and stamping its rows in one `UPDATE … SET <x>_notified_at … RETURNING`; logged only when it did something) are the only timer-driven code; `JobsScheduler` registers them (04:00 UTC and `*/5`, through `SchedulerRegistry`, never `@Cron`) only when `JOBS_ENABLED` is true (default; `false` in the test env and on every API container but one). A job is a method on the module that owns the table, takes the clock as a parameter (`deleteExpired(now)`, `deleteOrphans(before)`, `warnUnverified(before, now)`, `eraseUnverified(before)`) so tests run it with a date of their own, never `now()` in SQL, returns a count and must not throw for one bad row; `runDaily` logs each count and goes on after a failure. Add a new job as one more entry in the `jobs` (or `frequentJobs`) list, with an integration test in `test/jobs.int-spec.ts`. Retention: tokens by `expires_at`, uploads nobody attached within 24 h, unconfirmed accounts erased after 30 days with one warning mail at day 23 (`users.expiry_warned_at`); `AccountService.erase` is the shared erasure of a user (the member's own `delete` adds the password check and the last mail).
- Notifications (ADR 0015): `notifications/` owns the table; `NotificationsListener` (the twin of `ActivitiesListener`) turns `post.liked`, `comment.created`, `comment.reacted` (first reaction of a person on a comment only), `user.followed` and `user.mentioned` into rows through `NotificationsService.notify` (skips the actor's own doing, refreshes the existing row of the same `(user, type, actor, post, comment)` instead of adding one, emits `notification.created` → gateway `notification:new` to the recipient's room) and `retract` on unlike/unfollow. Comment types store `postId` too, so the link is `/p/:postId?comment=`. Routes: `GET /notifications`, `GET /notifications/unread-count`, `POST /notifications/read`, `POST /notifications/:id/read`; rows older than 90 days are a daily job. A new event that concerns a person = one `@OnEvent` in the listener + one sentence in `features/notifications/notification-text.tsx`. Web: `ChatProvider` hands the push to `receiveNotification` (`use-notifications.ts`: tops `queryKeys.notifications.list`, bumps `.unread`); `NotificationBell` in the header, the nav entry's badge and the tab title share `useUnreadNotifications()`; `/notifications` marks all read once its first page is on screen and leaves the loaded rows' `readAt` alone so the unread tint stays until the next visit. Chat stays out of notifications.
- Web push (ADR 0022): `push/` (`PushService`, `PushListener`, `PUSH_SENDER` = `WebPushSender` over `web-push`, swapped for a fake in `test/push.int-spec.ts`) sends `notification.created` (text from `NOTIFICATION_PHRASES` in shared, which the web's `NotificationText` uses too: a new notification type is one entry there) and `message.sent` to `push_subscriptions`, detached from the request; on only with `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` (all or none; `GET /push/config` answers `publicKey: null` otherwise). A subscription belongs to a sign-in: `refresh_tokens.sign_in_id` is carried along rotation and is the access token's `sid` (`AuthUser.signInId`); every way sessions end emits `SessionsEndedEvent` and `pruneEnded` drops the devices of sign-ins without a live token (plus a daily job for expiry). Endpoints must be a known push service (`isPushServiceUrl`, SSRF guard). Account preferences `pushMessages`/`pushSocial`/`pushPreviews`; settings are merged generically in `UsersService.updateSettings`, so a new key only goes in the shared schema. Web: `public/sw.js` (push only, no caching; shows a push only when no app window is visible; a click routes the open tab through `postMessage`), `public/manifest.webmanifest` with the icons `pnpm brand` writes, `lib/push.ts` (registration, subscribe, `beso.push.owner` in `localStorage` so another member never inherits a browser's subscription, `pushActiveHere()` which makes `MessageAlerts` leave the system notification to the worker), lazy `PushSync` in `AppShell` (re-sends the subscription on every start, re-subscribes after a key change), Settings → Notifications (`features/push/push-settings.tsx`), `lib/install-prompt.ts` (the install offer for Settings and the account menu). Tests stub `navigator.serviceWorker`, `PushManager` and `Notification` (`features/push/push-settings.test.tsx`); Playwright's headless shell has no notifications.
- Achievements (ADR 0021): badges live in `packages/shared/src/achievements.ts`, published as the entry `@beso/shared/achievements` (never re-exported from the main entry, so the web imports it only from lazy badge screens and the first paint stays small): one definition per badge (`key`, group, series, threshold, tier, title, description, lucide icon name, hidden); tiers are separate keys `<series>-<threshold>`. `achievements/`: `AchievementCounter` counts a series (one indexed count; a new series is one `case`, the `never` default makes a missing one a type error), `AchievementsService.check(userId, series[], now)` awards every badge reached and not held (`createManyAndReturn` + `skipDuplicates`; "All set" and Collector settle last) and notifies `ACHIEVEMENT_EARNED` without an actor; **earned is earned**, nothing removes a row but the erasure. `AchievementsListener` maps events to series, for the doer and for whoever the doing concerns (a new badge driven by an event = one entry in the catalogue + maybe one line there); the daily `sweep` re-checks everyone and alone does "Around the clock". Words and the clock are checked in JavaScript (`achievements/content-checks.ts`; the counter's `History` loads the member's posts, comment and message times once per check): local time comes from `settings.timeZone` through `localTime` (shared `time-zone.ts`, `Intl`), never `AT TIME ZONE` in SQL, and the clock badges count nothing without a zone; the shell saves the device's zone when missing (`useTimeZoneSync`), Settings → Time zone changes it, and there is no "none". Series whose badges are all hidden stay out of `progress`; badge icons should not be icons the first paint uses (a shared one is split into its own chunk). `users.achievements_checked_at` null = never counted: the first check awards silently (pre-F2 accounts and the seed); new accounts default to now. Notifications may have `actor: null` (badges only): the silencing filter is `actor_id IS NULL OR NOT IN`, push skips them, the web renders the medallion and `achievementSentence`. Settings `showAchievements` / `hideGettingStarted`. Web: "Badges" in the interface (`/u/:username/badges`, `/badges` → own tab), `Medallion` with the `--badge-*` tier tokens, `BadgeStrip`, the lazy `GettingStartedCard` on Home, `showBadgeToast` loaded on a pushed badge; tests use `mockDb.achievements` / `mockDb.achievementProgress` and `makeBadgeNotification`; integration tests about other notifications call `holdEveryBadge(prisma, ...users)` so no badge rows join their lists.
- Domain events: services `await this.events.emitAsync(Event.EVENT, new Event(...))` (classes in `src/events/`, names `<entity>.<past tense>` such as `post.liked`, `profile.updated`, `sessions.revoked`), so listeners finish before the response. Listeners (`@OnEvent`) must never throw; wrap their work in try/catch and log. `ActivitiesListener` is the model.
- Lists: keyset pagination everywhere (`cursorQuerySchema` in shared; `decodeCursor` → `{ createdAt, id }`, `keysetAfter(cursor, idWhere)` in the `where`, `paginate`/`paginateBy` in `common/pagination.ts`; order `createdAt desc, id desc`, fetch `limit + 1`). Never use Prisma's `cursor:` option: it breaks when the cursor row is deleted and drops the SQL `LIMIT` on composite keys. Feed-style items are shaped by a `select` function that takes the viewer id (e.g. `postSelect(viewerId)`) so counts and `likedByMe` come from the same query; map rows with the module's `to*` mapper.
- Comment replies (C2): one level only — `comments.parent_id` names a top-level comment, `POST /posts/:postId/comments` takes `parentId` (same post; a reply to a reply is folded under its parent by `CommentsService.parentFor`, a bad one is a field error), `GET /comments/:id/replies` lists them oldest first (`keysetAfterAscending`), `listForPost` keeps `parentId: null`, `replyCount` is `_count.replies` and the post's `commentCount` counts both; deleting a comment cascades to its replies. `CommentCreatedEvent` carries `parentId`/`parentAuthorId`: the notifications listener sends `COMMENT_REPLIED` to the parent's author (and `POST_COMMENTED` to the post's author unless that is the same person), and the service leaves the parent's author out of the mention events. Web: threads fold by default (`CommentThread` in `comments-section.tsx`), `useReplies(commentId, enabled)` under `queryKeys.comments.replies` (prefix `allReplies`, reached by `updateCommentEverywhere`), `useDeleteComment` takes the whole comment (its `replyCount` leaves the post count too), `useCreateComment` appends a reply to a fully loaded thread (`appendItem`), the composer prefills `@username` when a reply is answered.
- Edits and reactions: editing a post or comment (author only) stores the previous text in `post_revisions` / `comment_revisions` and stamps `editedAt`; an unchanged text is a no-op. Comment reactions are one row per member and comment (`comment_reactions`, enum `ReactionType`, display data in `REACTIONS` in shared) and keep `comments.reactions_count` in step inside the same transaction; `?sort=top` orders by that column with a ranked cursor (`encodeRankedCursor`, `paginateWith`). Per-type counts come from one `groupBy` per page (`CommentsService.countsFor`). On the web, `InlineEditor` is the edit-in-place component, `EditedMarker` the history popover, `ReactionBar` the pills + picker; comment caches are keyed by `(postId, sort)` and changed through `features/comments/use-comments.ts` only. Per-item controls (the "Add reaction" smiley and the options menu on a message bubble or a comment) exist for fine pointers only and appear on hover of the item, on keyboard focus inside it or while their popover is open; on coarse pointers they are `pointer-coarse:hidden` and a press-and-hold on the bubble opens the picker over it with the same options (edit/delete, report) listed under the emojis (`LongPressArea` in `components/`, `useLongPress` in `lib/use-long-press.ts`: finger or pen only, 350 ms so it beats the browser's own long-press whose context menu is always suppressed in the area, a scroll cancels, the release click is swallowed; `ReactionPicker`/`ReactionBar` take `pressedOn`/`onClose`/`actions`); the bubbles give up text selection on coarse pointers for it. Add a new per-item action to both the menu (or the hover toolbar, as a chat picture's "Download picture") and the `actions` list. Double tap to like (R6): `useDoubleTap` (`lib/use-double-tap.ts`) on the post card's body, finger or pen only, two taps within 300 ms and 30 px like (never unlike) and leave the `like-burst` heart (`index.css`, none with reduced motion); links and buttons keep their taps unless marked `data-double-tap` (the picture buttons), whose own action goes through `single()` and so waits 300 ms on touch; the area is `touch-manipulation`. A press that starts on a button belongs to the button, unless it carries `data-long-press` (a chat picture: a tap opens it, a hold is the message's).
- Text entities (ADR 0013): `tokenize` / `extractEntities` in `packages/shared/src/text.ts` are the only parser for `@mentions`, `#hashtags` and links; never parse them elsewhere. The API resolves mentions to members when a post or comment is saved or edited (`UsersService.findByUsernames`; unknown names are ignored), stores them in `post_mentions` / `comment_mentions` / `post_hashtags` (replaced as a whole on edit; tag rows copy the post's `createdAt` for the keyset), emits `UserMentionedEvent` only for members new to the text and never for the author (`common/mentions.ts`), and answers `mentions: UserSummary[]` (resolved at read, so renames hold) on posts and comments plus `hashtags` on posts. Tag routes live in `tags/` (`GET /tags/:tag/posts`, `GET /tags/trending`, `GET /tags/suggest?q=` for the `#` autocomplete: prefix among the last 90 days' posts, most used first, at most 8; `TagParamDto` folds the case and tolerates a leading `#`). Account preferences: `users.settings` JSONB validated by `userSettingsSchema` (defaults applied at read, unknown keys dropped), `PATCH /users/me/settings`, `useUpdateSettings` (optimistic) and the Settings → Chat card; add new preference keys to the shared schema, never to `localStorage`. Responsive logic uses `useMediaQuery(MD_UP)`; in tests `window.innerWidth = 390` before rendering makes width queries phone-sized.
- Web routing/perf: new pages are `lazy` routes in `app/router.tsx`; a feature with several route components exports them from one `routes.tsx` so they share a chunk. Keep the first paint small: `pnpm build` fails when the initial JavaScript passes the budget in `scripts/bundle-budget.mjs` (260 kB gz; raise it only with a reason in the PR, recorded in the script; a big shared module used only by lazy screens belongs in an entry of its own, like `@beso/shared/achievements`). `manualChunks` in `vite.config.ts` pins the long-lived runtimes (react, the router, `next-themes`, lucide's icon factory, `clsx`/`tailwind-merge`) into the `react` chunk: left to the bundler they get re-sliced into extra initial files whenever a lazy chunk's imports change shape, and that glue alone can break the budget (seen with the emoji picker swap, 2026-10-28). Heavy optional UI (emoji picker, socket client) is imported dynamically. After a deploy an open tab's lazy chunks are gone: `RouteError` and the `vite:preloadError` listener in `main.tsx` reload once (`lib/new-version.ts`), and Caddy (`apps/web/docker/Caddyfile`) serves `index.html` with `no-cache` and missing `/assets/*` as uncached 404s, never as HTML.
- Emoji picker (ADR 0023): `features/emoji/`. `EmojiPickerButton` (fine pointers only, `pointer-coarse:hidden`: a phone's keyboard has its own emoji panel) opens the lazy `EmojiPickerPanel` (frimousse, headless and virtualised, dressed with the tokens; one pick closes it and the composer keeps the caret). Its data is emojibase's `en/data.json` + `messages.json` as hashed assets of the build (`?url`) read by `resolveEmojiData` in `emoji-data.ts` (never the CDN frimousse defaults to), minus what the browser cannot draw (`emoji-support.ts`: a canvas check per Unicode release, and the country flags on Windows); `recent-emoji.ts` keeps the browser's last picks in `localStorage` (a device convenience, not an account preference). Tests mock `./emoji-data` (the canvas check never runs in jsdom); `e2e/emoji.spec.ts` picks for real.
- Web accessibility: every page must pass `e2e/a11y.spec.ts` (axe, WCAG 2.1 A/AA, light and dark); add new pages to it. Icon-only controls need `aria-label`; controls with visible text must keep that text in their accessible name; scrollable regions get `tabIndex={0}`; colours stay within the tokens (contrast was checked for them). Focus moves to `<main>` after navigation from the shell, so pages should start with their heading. Beyond axe (review 2026-10-19): a Radix overlay that navigates must prevent `onCloseAutoFocus` so focus lands on the new page; an editor or dialog that unmounts the focused control returns focus (`lib/focus.ts` `focusLater`); live announcements are `<output>` elements (never a live region on a whole list; the message log is `aria-live="off"` and announces one line per new message); counters use `CharacterCounter`; card titles that are headings use `<CardTitle asChild><h2>`.
- Web legal: `/privacy` and `/terms` live in `features/legal/` (plain TSX, `LegalLayout`/`LegalSection`/`LegalList`); operator, contact and repository come from `lib/env.ts` (`VITE_OPERATOR_NAME`, `VITE_CONTACT_EMAIL`, `VITE_REPOSITORY_URL`, build-time). When the wording changes, bump `LEGAL_UPDATED_ON`. They are linked from `AuthLayout`, the register consent line, Settings → About, the account menu and `SiteFooter` in the right bar.
- Ready-made pictures (R7, ADR 0021 amendment "ready-made pictures"): the catalogue is `@beso/shared/pictures` (its own entry: import it only from lazy screens and the API), `users.avatar_preset` / `cover_preset` hold an id, an upload and a preset exclude each other (`UsersService.updateProfile` clears the other; `assertPreset` checks the catalogue and the unlocking badge), URLs come from `pictureUrl` in `users.mapper.ts` (`<assets>/preset/<kind>-<id>.webp`, `GET /uploads/preset/:file` reads `apps/api/presets`, not storage; in production Caddy serves the rest of `/api/v1/uploads/*` from the volume itself, so `apps/web/docker/Caddyfile` sends `/api/v1/uploads/preset/*` on to the API). Registration takes an optional free `avatarPreset`. Web: `PicturePicker` (radio group; `lockOf` from `preset-locks.ts` shows the earned ones locked, without it only the free ones), on the register form with "Your initials" first and under each `ImageField` of the profile editor ("Choose one of ours"); `presetUrl` in `lib/presets.ts`. A preset counts for the picture badges.
- Badge rewards (R8, ADR 0021 amendment "rewards"): the avatar ring is the Collector tier (10/25/50/75 → bronze…platinum) stored in `users.ring` by `refreshRing` (`users/ring.ts`: on a Collector award in `AchievementsService.award`, and when `showRing` or `showAchievements` changes in `updateSettings`) and carried by every `UserSummary` (`ring`; `UserAvatar` outlines it with the `--collector-*` tokens, `data-ring` for tests, so any new place that builds a summary must pass it); featured badges are `users.featured_badges` (`PUT /users/me/featured-badges`, `useFeatureBadges`, `UserPublic.featuredBadges` empty while badges are hidden, `BadgeStrip featured`); a post may share a held badge (`achievementKey` → `Post.achievement`, the lazy `PostBadge` card); `showBadgeToast(key, openBadges, share)` throws `celebrate()` confetti and its "Share" goes to `/badges?share=<key>` (the redirect keeps the query, `MyBadges` opens `ShareBadgeDialog`).
- Pinned post (R6): `users.pinned_post_id` (unique, SET NULL), `PUT`/`DELETE /posts/:id/pin` (author only, another pin replaces it, unpinning another post is a no-op), `pinnedPostId` on every profile (null across a block, so `UserPublic` fixtures need it). Web: the post menu's "Pin to your profile" / "Unpin from your profile" (`usePinPost` patches `me` and the profile caches), `ProfilePosts` loads the pinned post through `postQueryOptions` and passes it to `PostList` as `pinned` (first, with `PostCard pinned`, and left out further down).
- Web profile: `/u/:username` is a layout route; tab routes read the loaded user with `useProfileContext()`. Profile edits go through `buildProfilePatch` (diff only) and `useUpdateProfile`; pictures through `ImageField` + `useImageUpload(kind)`.
- Web dev/preview proxy `/api` and `/socket.io` to `VITE_DEV_API_URL` (default `http://localhost:3000`), so the app is same-origin with the API and cookies just work; leave `VITE_API_URL` empty unless the API really lives elsewhere.
- Web tests: Vitest + jsdom + Testing Library + MSW (`src/test/setup.ts` starts the server with `onUnhandledFrame: 'error'`, so every request a test triggers needs a handler in `src/test/msw/handlers.ts` or a `server.use(...)` in the test). `renderApp(route)` mounts the real router + providers; `renderWithProviders(ui)` for single components; `signedInAs(user)` sets the mocked session (`mockDb.user` is the signed-in user, null for none). Query by role/label, never by class. Mock data: `mockDb` (users alice/bob/carol, follows, posts, comments, uploads) + `seedPosts()` / `seedFollow()` + fixtures (`makePost`, `makeComment`, `alice`/`bob`/`carol`); `mockDb.user` is the signed-in user, `toPublic()` derives the public shape; the setup swaps `FormData`/`Blob`/`File` for Node's (MSW runs on Node's fetch), stubs `URL.createObjectURL` and installs a controllable `IntersectionObserver` (`intersectAll()` from `src/test/intersection-observer.ts`); pass `{ applyAccept: false }` to `user.upload` for files the input's `accept` would filter. Playwright specs live in `apps/web/e2e/`: the `seed` project reseeds the database, the `setup` project signs in alice, bob and carol once and stores cookies (`e2e/.auth/`, gitignored); specs start signed in as alice and call `openHome(page)`, open another member with `contextAs(browser, 'bob')`, and use `test.use({ storageState: ANONYMOUS })` only when the sign-in flow itself is under test (helpers in `e2e/helpers.ts`, fixtures in `e2e/fixtures/`). Never trigger a token refresh with the shared session (single-use refresh tokens); clean up data other specs rely on; scope locators (`exact: true`, `within` a region) because the sidebar renders Follow buttons too.
- Secrets only via environment variables; commit `.env.example` files, never `.env`. First run: `cp apps/api/.env.example apps/api/.env`.
- Database: schema lives in `apps/api/prisma/schema.prisma` (UUID v7 ids, snake_case via `@map`, `timestamptz`). Every schema change ships with a migration in the same PR (`pnpm db:migrate --name <change>`); never edit an applied migration. Prisma config is `apps/api/prisma.config.ts` (Prisma 7: no `url` in the schema, `.env` loaded there via dotenv).
- Integration tests (`pnpm test:int`) need Docker: they start a throwaway Postgres with Testcontainers unless `TEST_DATABASE_URL` is set (CI). They ignore `DATABASE_URL` on purpose and truncate the tables they use. The harness sets `DOCKER_AUTH_CONFIG` to an empty anonymous config because only public images are pulled; this also sidesteps Docker Desktop's Windows credential helper, which cannot be spawned from WSL (`appendWindowsPath = false`).
- `.pnpmfile.cjs` (a `readPackage` hook) removes a few optional peers before resolution; changing it changes `pnpmfileChecksum` in the lockfile, and every Dockerfile copies it next to the lockfile or the frozen install fails.
- pnpm 11 only runs approved postinstall scripts (`allowBuilds` in `pnpm-workspace.yaml`). When a new dependency brings a build script, pnpm inserts a placeholder line `'<pkg>': set this to true or false` into that file and fails fresh installs until it is replaced with `true` or `false` (deny telemetry/optional native builds, allow only what the app needs). A local `pnpm install` that is "already up to date" skips this check, so verify with a clean install: `git worktree add /tmp/wt HEAD && cd /tmp/wt && pnpm install --frozen-lockfile`. `pnpm approve-builds` also rewrites the file and can drop the catalog; re-check it afterwards.

- Deployment: images are built by `.github/workflows/docker.yml`, a reusable workflow that `ci.yml` calls only after the checks, integration and e2e jobs passed (pull requests build without pushing), and pulled by the server (`deploy/update.sh` on a systemd timer); there is no push deploy. Runtime configuration is environment only (`deploy/.env.example`); the API refuses development defaults in production (`PUBLIC_ASSETS_URL`, `WEB_ORIGINS`, `TRUST_PROXY`, `WEB_URL`, `EMAIL_FROM`, `SMTP_URL`, `EMAIL_TRANSPORT=smtp`, `TURNSTILE_SECRET` unless `CAPTCHA=off`, placeholder `JWT_SECRET` or `TURNSTILE_SECRET`, any falsy `COOKIE_SECURE`); optional variables that compose passes as empty strings count as unset. Migrations run in the one-shot `migrate` service (image `beso-migrate` from `apps/migrate`, entrypoint `prisma`, default command `migrate deploy`): compose runs it to completion before the API (`service_completed_successfully`), and `update.sh` runs it on its own first so a failed migration leaves the running release up. The API image carries no Prisma CLI: `prisma` and `dotenv` are devDependencies of the API, and `.pnpmfile.cjs` drops the optional peers (`@prisma/client` → `prisma`, `typescript`; `@nestjs/swagger` → `typescript`) that would otherwise put them back into `pnpm install --prod`. `update.sh` pulls only `migrate api web` (all or nothing) and applies changes only when the config or an image changed (`.update-state`); `postgres` and `cloudflared` are updated by hand (RUNBOOK §6).
